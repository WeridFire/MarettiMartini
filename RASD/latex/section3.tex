\section{Specific Requirements}
This section contains the detailed requirements for the Best Bike Paths (BBP) system. It provides a comprehensive description of the external interfaces, functional requirements, and non-functional constraints necessary for the development team to implement the solution.

\subsection{External Interface Requirements}
This subsection describes how the system interfaces with users, hardware, other software, and communications.

\subsubsection{User Interfaces}
The system is primarily accessed via a mobile application (Android/iOS). The user interface must be designed to be minimal and high-contrast to ensure legibility while cycling (Safety Critical).

\begin{itemize}
    \item \textbf{Map Visualization:} The UI shall display a map as the central element, rendering paths with color codes indicating their status (e.g., Green for ``Optimal'', Red for ``Poor'').
    \item \textbf{Controls:} Buttons for starting/stopping trips and reporting anomalies must be large and easily tappable to facilitate interaction during physical activity.
    \item \textbf{Notifications:} The system shall use non-intrusive notifications (audio cues or heads-up alerts) for automated detection alerts to minimize user distraction.
\end{itemize}

\subsubsection{Hardware Interfaces}
The mobile application interacts directly with the smartphone's hardware sensors to fulfill the automated data collection goals.

\begin{itemize}
    \item \textbf{GPS Receiver:} Used to track geolocation (latitude, longitude, altitude) and calculate real-time speed.
    \item \textbf{Accelerometer \& Gyroscope:} Used to detect vertical accelerations and device orientation changes indicative of road anomalies (e.g., potholes) or specific cycling movement patterns.
    \item \textbf{Local Storage:} The device's file system is used to buffer trip data and sensor logs temporarily when an internet connection is unavailable.
\end{itemize}

\subsubsection{Software Interfaces}
The BBP system interacts with the following external software entities:

\begin{itemize}
    \item \textbf{Map Service API} (e.g., Google Maps, OpenStreetMap): Used to retrieve map tiles and access the underlying road network topology.
    \item \textbf{Weather Service API:} Used to fetch meteorological data (Temperature, Wind Speed, Weather Condition) based on the specific timestamp and location coordinates of a trip.
    \item \textbf{Operating System} (Android/iOS): The app interfaces with the host OS to manage permissions (Location Always On, Background Processing) and utilize system notification services.
\end{itemize}

\subsubsection{Communication Interfaces}
\begin{itemize}
    \item \textbf{Protocol:} Communication between the Mobile Client and the Backend Server shall occur over HTTPS to ensure data confidentiality and integrity.
    \item \textbf{Data Format:} Data exchange (e.g., trip uploads, route requests) shall use JSON format over RESTful APIs.
\end{itemize}

\subsubsection{Requirements}
This subsection summarizes the goals described in section \ref{goals}, mapping them to specific functional requirements and domain assumptions.

\begin{enumerate}[label=\textbf{-[G\arabic*]}:]
    
    \item \textbf{Allow registered users to track their cycling activity}
    \begin{itemize}
        \item \textbf{[R1]:} The system allows Unregistered Users to sign-up providing personal details.
        \item \textbf{[R2]:} The system allows Registered Users to log-in to access their personal dashboard.
        \item \textbf{[R3]:} The system allows users to manually start and stop the recording of a trip via the application interface.
        \item \textbf{[R4]:} The system continuously tracks the user's geolocation (GPS coordinates) and time during the recording.
        \item \textbf{[D\_ASS1]:} GPS Availability - It is assumed that the GPS signal is available and sufficiently accurate to allow for meaningful path reconstruction.
    \end{itemize}

    \item \textbf{Provide detailed statistics on trip performance}
    \begin{itemize}
        \item \textbf{[R2]:} The system allows Registered Users to log-in.
        \item \textbf{[R5]:} The system processes raw GPS data to calculate performance metrics, specifically total distance and average speed.
        \item \textbf{[R6]:} The system displays a summary of the statistics immediately after a trip is stopped.
        \item \textbf{[R7]:} The system archives the trip statistics in the user's personal history for future retrieval.
    \end{itemize}

    \item \textbf{Enrich trip data with contextual information}
    \begin{itemize}
        \item \textbf{[R8]:} The system connects to an external service to retrieve meteorological data (temperature, wind, condition) based on the trip's timestamp and location.
        \item \textbf{[R9]:} The system merges the retrieved weather data with the trip statistics.
        \item \textbf{[DEP2]:} External Weather Service - The system depends on the availability of an external API to fetch real-time and historical meteorological data.
        \item \textbf{[DEP3]:} Mobile Data Connectivity - The system depends on the mobile network to fetch weather data.
    \end{itemize}

    \item \textbf{Enable manual reporting of path status}
    \begin{itemize}
        \item \textbf{[R2]:} The system allows Registered Users to log-in.
        \item \textbf{[R10]:} The system allows users to select a specific location or segment on the map.
        \item \textbf{[R11]:} The system allows users to input status details (e.g., ``Requires Maintenance'') and obstacle types.
        \item \textbf{[R12]:} The system saves the manual report to the user's personal records.
        \item \textbf{[D\_ASS5]:} User Integrity - It is assumed that the majority of users provide truthful manual reports regarding path conditions.
    \end{itemize}

    \item \textbf{Automate data collection via mobile sensors}
    \begin{itemize}
        \item \textbf{[R13]:} The system monitors device sensors (accelerometer and gyroscope) in the background while the user is cycling.
        \item \textbf{[R14]:} The system identifies potential road anomalies (e.g., potholes) based on vertical jolts and orientation changes.
        \item \textbf{[R15]:} The system logs the anomaly type and location internally for later verification.
        \item \textbf{[D\_ASS2]:} Device Sensor Capability - It is assumed that users' smartphones are equipped with functioning accelerometers and gyroscopes.
        \item \textbf{[D\_ASS3]:} Device Placement - It is assumed the phone is placed in a position (e.g., pocket, handlebar) that allows perceiving vibrations.
    \end{itemize}

    \item \textbf{Ensure accuracy of automatically detected data}
    \begin{itemize}
        \item \textbf{[R16]:} The system notifies the user after a trip if potential anomalies were detected.
        \item \textbf{[R17]:} The system displays a map or list of detected anomalies for verification.
        \item \textbf{[R18]:} The system allows the user to explicitly ``Confirm'' or ``Reject'' (False Positive) a detected anomaly.
        \item \textbf{[R19]:} The system discards data marked as ``Reject'' and stores data marked as ``Confirm'' as valid path information.
        \item \textbf{[D\_ASS5]:} User Integrity - It is assumed that users generally provide truthful confirmations.
    \end{itemize}

    \item \textbf{Enable the publication of collected information}
    \begin{itemize}
        \item \textbf{[R2]:} The system allows Registered Users to log-in.
        \item \textbf{[R20]:} The system allows users to select validated data (manual or automated) from their history.
        \item \textbf{[R21]:} The system allows users to mark specific data as ``Publishable''.
        \item \textbf{[R22]:} The system updates the public inventory with the published path quality data.
        \item \textbf{[CON1]:} Regulatory \& Privacy - Private trips must remain inaccessible unless explicitly published.
    \end{itemize}

    \item \textbf{Support route planning for all users}
    \begin{itemize}
        \item \textbf{[R23]:} The system allows both Registered and Unregistered users to access the ``Explore'' section.
        \item \textbf{[R24]:} The system allows users to input an Origin and a Destination.
        \item \textbf{[R25]:} The system calculates available routes between the two points.
        \item \textbf{[DEP1]:} External Map Service - The system depends on a third-party Map Provider for road network topology.
    \end{itemize}

    \item \textbf{Evaluate and rank available paths}
    \begin{itemize}
        \item \textbf{[R25]:} The system calculates available routes.
        \item \textbf{[R26]:} The system computes a ``Path Score'' for each route based on path status (from the public inventory) and efficiency.
        \item \textbf{[R27]:} The system visualizes the routes on the map, highlighting the highest-scored path.
        \item \textbf{[R28]:} The system displays a summary of the route details (distance, estimated time, score).
    \end{itemize}

    \item \textbf{Detect cycling activity automatically}
    \begin{itemize}
        \item \textbf{[R29]:} The system periodically monitors GPS speed in the background.
        \item \textbf{[R30]:} The system automatically triggers the ``Start Recording'' function when the speed exceeds a specific cycling threshold for a sustained period.
        \item \textbf{[R31]:} The system automatically stops the recording when the user stops moving for a defined timeframe (e.g., 5 minutes).
        \item \textbf{[D\_ASS4]:} Distinguishability of Speed - It is assumed that cycling speeds are sufficiently distinct from walking and driving to allow automated inference.
    \end{itemize}

    \item \textbf{Protect user privacy while enabling collaboration}
    \begin{itemize}
        \item \textbf{[R32]:} The system stores all recorded trips as ``Private'' by default.
        \item \textbf{[R33]:} The system anonymizes personal identifiers before transferring data to the public inventory during the publication process.
        \item \textbf{[CON1]:} Regulatory \& Privacy - The system must ensure no personal trip data is exposed unless explicitly published.
    \end{itemize}

\end{enumerate}

\subsection{Performance Requirements}
The Best Bike Paths (BBP) system must ensure fluid interaction and accurate tracking, balancing data precision with battery efficiency.

\begin{itemize}
    \item \textbf{[PR1] Response Time:} The mobile application shall maintain a high responsiveness. Interactions such as starting/stopping a recording or navigating menus should have a latency of less than \textbf{1 second}.
    \item \textbf{[PR2] Route Calculation Latency:} When a user requests a route (Scenario 7), the system should retrieve and visualize the calculated paths within \textbf{3 seconds} under normal network conditions.
    \item \textbf{[PR3] Sensor Data Frequency:} To accurately detect anomalies (potholes/bumps) via the ``Automated Mode'' (Scenario 3), the application must poll the accelerometer and gyroscope at a minimum frequency of \textbf{50 Hz} while the vehicle is in motion.
    \item \textbf{[PR4] Location Tracking Accuracy:} During trip recording, GPS coordinates must be sampled at a minimum rate of \textbf{1 point every 5 seconds} or \textbf{every 10 meters}, with a horizontal accuracy within 10 meters.
    \item \textbf{[PR5] Concurrent Users:} The backend system shall support at least \textbf{1,000 concurrent users} sending telemetry data or requesting routes without service degradation.
    \item \textbf{[PR6] Offline Buffering:} The mobile application must be capable of buffering at least \textbf{24 hours} of trip data and sensor logs locally in case of connectivity loss.
    \item \textbf{[PR7] Battery Consumption:} The background activity detection and recording service must be optimized to consume no more than \textbf{10\% of the device battery per hour} of active tracking.
\end{itemize}

\subsection{Design Constraints}

\subsubsection{Standards compliance}
\begin{itemize}
    \item \textbf{[DC1] GDPR Compliance:} In accordance with [CON1], all personal data (trip history, precise geolocation) must be stored in compliance with the General Data Protection Regulation (GDPR). The system must allow users to export or delete their data upon request.
    \item \textbf{[DC2] Map Standards:} The system must utilize standard geospatial data formats (e.g., GeoJSON) for storing and exchanging path and anomaly data.
    \item \textbf{[DC3] Communication Security:} All data transmission between the mobile client and the backend server must be encrypted.
\end{itemize}

\subsubsection{Hardware limitations}
\begin{itemize}
    \item \textbf{[DC4] Smartphone Sensors:} The application requires the user's device to be equipped with a functioning \textbf{GPS/GNSS receiver}, \textbf{accelerometer}, and \textbf{gyroscope}. The system cannot function fully on devices lacking these sensors.
    \item \textbf{[DC5] Storage Limits:} To respect device storage limitations, the local buffer for offline trips (DC3) shall utilize a circular buffer or a compression mechanism, capping local storage usage at \textbf{500 MB}.
    \item \textbf{[DC6] Battery Consumption:} The ``Automated Mode'' and background tracking must be optimized to not drain more than \textbf{10\% of the device's battery per hour} of active usage.
    \item \textbf{[DC7] Device Placement:} As noted in Domain Assumption \textbf{[D\_ASS3]}, the accuracy of pothole detection is constrained by the physical placement of the phone.
\end{itemize}

\subsubsection{Any other constraint}
\begin{itemize}
    \item \textbf{[DC8] OS Compatibility:} The mobile application must be compatible with \textbf{Android 10.0+} and \textbf{iOS 14.0+} to ensure access to modern background processing APIs required for Requirement R7[cite: 311].
    \item \textbf{[DC9] Network Dependency for Enrichment:} The weather enrichment feature (Scenario 2) and route planning (Scenario 7) are strictly dependent on an active internet connection. These features are disabled in offline mode.
\end{itemize}

\subsection{Software System Attributes}

\subsubsection{Reliability}
\begin{itemize}
    \item \textbf{[SSA1] Data Persistence \& Integrity:} The system must ensure \textbf{zero data loss} for recorded trips. In the event of an application crash or unexpected shutdown (e.g., battery depletion), the current trip state must be recoverable from the local storage upon the next launch.
    \item \textbf{[SSA2] Detection Accuracy:} The automated anomaly detection algorithm should aim to minimize user fatigue by maintaining a False Positive rate below \textbf{20\%} (i.e., at least 80\% of detected anomalies should be real road defects).
\end{itemize}

\subsubsection{Availability}
\begin{itemize}
    \item \textbf{[SSA3] Offline Resilience:} The core tracking functionality (recording trips and collecting sensor data) must be \textbf{100\% available} regardless of network status. Synchronization with the server shall occur transparently when connectivity is restored.
    \item \textbf{[SSA4] Server Uptime:} The BBP Backend Server must guarantee \textbf{99.9\% uptime} during peak usage hours (06:00 - 22:00), ensuring users can always log in and sync their history.
\end{itemize}

\subsubsection{Security}
\begin{itemize}
    \item \textbf{[SSA5] Data Encryption:} All sensitive data transmission between the mobile client and the backend server (authentication, geolocation history) must be encrypted via HTTPS.
    \item \textbf{[SSA6] Privacy by Default:} All user trips are ``Private'' by default[cite: 325]. The system must ensure that no personal trip data is exposed to the public map unless the user explicitly executes the ``Publish Information'' use case \textbf{[UC7]}.
    \item \textbf{[SSA7] Authentication:} Access to personal history and reporting features requires secure login (Token-based authentication, e.g., \textbf{JWT}) to prevent session hijacking.
\end{itemize}

\subsubsection{Maintainability}
\begin{itemize}
    \item \textbf{[SSA8] Modular Architecture:} The ``Anomaly Detection Module'' must be decoupled from the main application logic[cite: 329]. This allows the development team to update or tune the detection algorithm (e.g., tweaking sensitivity thresholds) without requiring a complete overhaul of the mobile application.
    \item \textbf{[SSA9] Code Documentation:} The source code must follow standard documentation practices (e.g., Javadoc for Java/Android, SwiftDoc for iOS) to facilitate future handover to other developers in the association.
\end{itemize}

\subsubsection{Portability}
\begin{itemize}
    \item \textbf{[SSA10] Cross-Platform Consistency:} The mobile application must provide feature parity between the \textbf{Android} and \textbf{iOS} versions, ensuring that the sensor data collection behaves consistently across different operating systems[cite: 333].
    \item \textbf{[SSA11] Backend Deployment:} The server-side components should be containerized (e.g., using Docker) to allow deployment on any standard cloud infrastructure (AWS, Azure, or on-premise servers) without environment-specific configurations.
\end{itemize}
